# Calder Wheels — Development & Client Update Schedule

**Recommended routine** for staying responsive and keeping Ray informed throughout the 10–12 week build.

---

## Weekly Development Cadence

| Day | Focus | Notes |
|-----|-------|-------|
| **Monday** | Planning + architecture | Set weekly targets, review remaining blockers, update task tracker |
| **Tuesday** | Development sprint (deep work) | No meetings — primary building time |
| **Wednesday** | Development sprint + client touchpoint | Continue build + send brief mid-week status |
| **Thursday** | Development sprint | Deep work on configurator/integrations |
| **Friday** | Review + client update | End-of-week summary to client, update Notion project tracker |

**Recommended hours**: 5–6 focused hours per day, 4–5 days per week = 20–30 hours/week. This lands the 125–155 hour estimate within 6–8 weeks of active development.

## Client Update Routine

### Weekly Updates (Every Friday)

A structured Friday email to Ray covering:

1. **What was accomplished this week** (3–5 bullet points)
2. **What's planned for next week** (3–5 bullet points)
3. **Any blockers or items needing client input** (rendering assets, product data, approvals)
4. **Schedule status** — on track, ahead, or adjusted
5. **Attachments / links** — mockups, screenshots, staging URLs where applicable

**Tone**: Brief, confident, technical but accessible. No filler. Ray should feel like the project is moving and he's in control.

### Milestone Updates (As Reached)

When a milestone deliverable is ready for review, send a **dedicated update** outside the Friday rhythm:

1. **What's ready**: Link to staging / mockups / document
2. **What you're reviewing**: Specific items needing approval
3. **What happens next**: The next phase that starts upon approval
4. **Timeline impact**: Any adjustments from the original schedule

### Approval Requests

When Ray's feedback is needed to unblock work:

1. **State the decision clearly**: "Please confirm Option A or B for the [feature]"
2. **Explain the trade-off**: What each option means for timeline, cost, or quality
3. **Set a deadline**: "I need this by [date] to stay on schedule"
4. **Deadline is soft at first** — follow up once before escalating

### Urgent / Blocking Issues

If something is blocking development (missing assets, platform issue):

1. **Same-day notification** — email or text (per Ray's preference)
2. **State the blocker clearly**: What's needed and why
3. **Propose a workaround**: Option to proceed with a placeholder vs. wait for the real asset
4. **Timeline impact**: How many days this pushes the schedule

## Development Rhythm — Weekly Sprint Structure

```
Monday Morning:
├── Review last week's progress
├── Set this week's 3–5 objectives
└── Update task tracker

Monday–Thursday:
├── 2–3 deep work blocks per day
├── Wednesday: brief status note to client
└── Handle any client requests within 24 hours

Friday Afternoon:
├── Complete/review this week's work
├── Write Friday client update
├── Update Notion project tracker
├── Review next week's priorities
└── Push commits, close out week
```

## Proactive Client Management Principles

1. **Always be 1 step ahead** — send the next deliverable before they ask for it
2. **Bad news early** — if a timeline slips, inform immediately with a revised plan
3. **No surprises** — every milestone has a preview period before the formal review
4. **Client sees progress, not process** — update the Notion board so Ray can check in anytime
5. **Under-promise, over-deliver** — quote 12 weeks, aim for 10
6. **Response time target** — acknowledge client messages within 4 business hours
